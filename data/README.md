# The RNAWiki dataset

This directory contains a repaired, dated legacy snapshot of public medicine records. It is not a
live mirror and may not match the website's current records or fields. Check `generatedAt` in
`manifest.json` and read the known limitations below before using it.

A successful scheduled export replaces this directory from the authoritative database. That lets
readers inspect a dated copy of public medicine data and compare later exports over time.

## This directory is generated. Do not send pull requests to it.

Every file here is overwritten wholesale on each export. A change committed to `data/` disappears
at the next run.

That is deliberate. Public data changes in the database and is then regenerated by the export job;
editing a generated file would create a second, temporary version that disappears at the next run.
Programme conclusions use fixed software checks and exact-version human review. Older record fields
still use the clearly separate legacy workflow described on the site.

**To propose a change, start from the [medicine page](https://rnawiki.com/browse).** A change appears
in this directory only after the relevant review and publication steps finish and a later export
runs. How that works: [rnawiki.com/how-it-works](https://rnawiki.com/how-it-works).

Corrections to the _pipeline_ — the ingest, the enrichment, the checks — are very welcome as pull
requests. That is code, and it lives outside this directory.

## What is here

| File                     | What it is                                                         |
| ------------------------ | ------------------------------------------------------------------ |
| `manifest.json`          | Export time, legacy row counts, and each generated file's SHA-256  |
| `drugs.csv`              | Flat identity, regulatory, structure, trial-count, and URL columns |
| `drugs/drugs-NNN.ndjson` | Repaired legacy records in the snapshot's medicine-wide shape      |

Newline-delimited JSON, so you can stream it without loading 14 MB into memory:

```bash
cat data/drugs/*.ndjson | jq -c 'select(.modality == "siRNA (Small Interfering RNA)") | {slug, name}'
```

```python
import json
for line in open('data/drugs/drugs-001.ndjson'):
    drug = json.loads(line)
```

Keys are sorted inside each object, so a diff between two exports shows what actually changed
rather than a reshuffle.

## Verifying an export

```bash
python3 - <<'PY'
import hashlib, json, pathlib
manifest = json.load(open('data/manifest.json'))
for entry in manifest['files']:
    digest = hashlib.sha256(pathlib.Path(entry['path']).read_bytes()).hexdigest()
    print('ok  ' if digest == entry['sha256'] else 'BAD ', entry['path'])
PY
```

## Known limitation of this checked-in snapshot

Read `manifest.json.generatedAt` for the artifact timestamp. This is a repaired legacy snapshot,
not proof that a fresh database export ran at that time.

The legacy exporter that originally wrote these NDJSON files lost properties inside nested objects.
That left placeholders such as `{}` and `[{}]`, which conveyed no usable data. The snapshot repair
removed those empty shells; it did not invent or reconstruct missing properties. As a result,
object-valued fields can be absent and arrays of nested objects — including `aliases`, `trials`,
`mechanismSteps`, and `keyAudits` — can be empty even when database-derived counts in the manifest
or flat `trial_count` values in the CSV show that nested rows existed when the legacy export ran.
Only a fresh export from the authoritative database can restore those details.

The checksums, byte counts, and row counts in the manifest describe the repaired files that are
checked in now. Other legacy manifest counts were calculated from the database by the original
export and are retained because they cannot be recalculated from the damaged nested payload.

## Programme evidence in the next export

The checked-in repaired snapshot predates the normalized programme export shape. Its NDJSON rows do
not contain `programmeEvidence`, its CSV has no programme-binding columns, and its manifest has no
programme counts. The exporter code is set to add all three on a future successful run against the
authoritative database. Check `generatedAt`, the CSV header, and a sample NDJSON row to identify
which schema a local snapshot uses.

In the next-export schema, each NDJSON row has `programmeEvidence`, built from the same normalized
public projection used by the home and browse cards.

- `programmes[]` contains each development programme's id, slug, title, indication, population,
  and status.
- `programmes[].currentPublication` is present only when
  `programme_current_publications` points to that exact `PUBLISHED` verdict revision. It includes
  the revision number, publication time, public summary and scope, engine version, input and
  proposal SHA-256 digests, and sorted `sourceSnapshotIds`.
- `sourceSnapshotIds` covers immutable snapshots cited by the exact reviewed verdict claims,
  evidence-step claims, study-interpretability claims, mechanism and timeline claims, and scoped
  trial registrations. An empty array means that graph contains no stored snapshot id; it does not
  mean a source proves the linked statement or that older medicine-wide fields have source-level
  coverage.
- `selectedSummary.binding` says whether the compact card text came from a reviewed programme
  publication, an unpublished programme indication, or the legacy medicine identity/indication.
  The first case carries the same revision id and input digest as `currentPublication`.

If a programme has no authoritative current publication, the next-export projection does not borrow
the old medicine-wide verdict. The revised CSV is intentionally flatter: it carries the selected
programme slug and, when present, that programme's current revision id, revision number, input
digest, and semicolon-separated snapshot ids. Use a regenerated NDJSON snapshot when you need every
programme.

## The three record depths

Read `dossierDepth` before you read anything else. It says how much of a record a human has
touched, and the three levels mean very different things.

| `dossierDepth` | What it means                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `flagship`     | A deeply written legacy dossier. This depth does not by itself mean that a normalized programme conclusion is published.                                                             |
| `curated`      | An expanded record built from public sources. Individual fields may be automated or editorial; check their recorded sources and, when the snapshot includes it, `programmeEvidence`. |
| `stub`         | Primarily identity and regulatory information. Other fields may be unwritten.                                                                                                        |

`sourceProvenance` lists the upstream sources recorded for a medicine. It is not a claim-by-claim
proof and may be empty on a sparse record.

## Things worth knowing before you use this

- **An empty field means the export has no recorded value**, not that the answer is zero or none.
- **The old medicine-wide `oneSentenceVerdict` is intentionally omitted.** It has no safe
  programme scope. Once a snapshot contains `programmeEvidence`, use
  `programmeEvidence.programmes[].currentPublication` for a reviewed conclusion and preserve its
  programme binding.
- **Operational laboratory instructions are intentionally omitted.** The public export can include
  non-operational molecular identity and check results, but it does not publish the stored
  `molecularSchema.laboratoryWorkflow` field.
- **In a fresh export, `trials[].endpointMet: false` on a machine-added trial means "not
  recorded".** ClinicalTrials.gov carries registrations, not results — whether a trial worked is
  in the paper. The checked-in repaired legacy NDJSON cannot be used for nested trial detail; use
  its flat CSV `trial_count` only as the retained legacy count.
- **Prices are what pharmacies pay**, from the CMS National Average Drug Acquisition Cost survey,
  not what a patient is charged. US list prices are not published and net prices after rebates are
  confidential.
- **`isMachineVerifiedStructure` means the structure passed the engine**, not that the medicine
  works or the page is right. It also means less on a biologic, where there is no tractable
  structure to check, than on a small molecule.
- **A quoted label passage is marked as one** — it opens "From the FDA-approved label:". Those are
  the manufacturer's words to the regulator, not writing done for this site.

## Live API

If you want current data rather than a snapshot:

```
GET https://rnawiki.com/api/drugs?limit=60&offset=0&modality=Small%20Molecule
GET https://rnawiki.com/api/drugs/metformin
GET https://rnawiki.com/api/search?q=paracetamol
```

Rate limited to 60 requests a minute. For anything larger, use this directory — that is what it is
for.

## Where the underlying data comes from

openFDA (Drugs@FDA, the NDC Directory, SPL labels) · PubChem · ClinicalTrials.gov · the CMS
National Average Drug Acquisition Cost survey · the NIH Dietary Supplement Label Database · and,
for hand-researched records, the individual papers cited on each one.

These are public sources, but access conditions can change. Source coverage also varies by record;
inspect the identifiers and links actually stored with the medicine before relying on a statement.
