The database loaded the same corpus measure v12 read: tiers **1,697 / 3,787 / 23,173**, **293**

**What changed, and why each part was safe to remove.**

1. **The interaction line is one element.** It was
   `<li class="cd-interaction"><span class="cd-interaction-line">…</span></li>`. No rule in
   `lib/corpus/dossier.css` used `.cd-interaction`; `.cd-interaction-line` set one ink, which
   `.cd-interactions > li` now sets beside the `overflow-wrap: anywhere` the shared row rule already
   carried. Neither class is read by `dom_parity.py`, `rendered_dup_check.py`, `self_audit.py`,
   `jsonld_check.py` or `browser-checks.ts`; `self_audit.py` reads the list, `ul.cd-interactions`,
   which is unchanged. **63 bytes per published interaction row.**
2. **The provenance entry is one element per record, not three.** It was
   `<li><span class="cd-row-label">…</span> <span class="cd-row-id">…</span><div class="cd-row-value"><a>…</a></div></li>`.
   The label is now the row's own first words and the counterpart is the link beside the id, so the
   element that remains is the one a rule reads: `.cd-row-id`, which `self_audit.py`'s rule "no
   record id painted outside a closed disclosure" requires to sit inside a closed control and which
   `tests/unit/corpus-render-safety.test.ts` requires to appear nowhere else. §14(7) is kept: the
   space before the id and the space before the link are text nodes, so no extraction reads two of
   these values as one word, and `self_audit.py`'s rule "adjacent inline elements are separated by a
   text node" passes on 40 of 40 applications. **65 bytes per provenance entry**, one less where the
   entry carries a counterpart link. What a reader sees change: the label keeps its ink — `.cd-root`
   sets `--corpus-ink-0` and `.cd-row-label` set the same value — and loses the 600 weight, so the
   row reads at the disclosure's ordinary weight with the id still in small grey monospace beside
   it.
3. **The checked-source rows carry their text directly**, without a `.cd-row-value` block inside the
   list item (**32 bytes per row**), and the furniture mark moved from each of those rows to the list
   that holds them (**22 bytes per row after the first**). A page with no interaction row has no
   provenance entry either, so on exactly the pages where the mark applies the list holds nothing but
   those names: hiding the list hides what hiding each row hid, on both sides of every check that
   reads `[data-furniture]`.
4. **Two elements that painted nothing are gone**: the `cd-interactions-block` class on the section,
   which no stylesheet rule and no check reads, and the empty `<ul class="cd-interactions"></ul>` a
   tier rendered above its control when every one of its lines was disclosed.

**Whitespace.** The generated document holds **127 bytes** of inter-tag whitespace, every one of them
a single space and every one of them a §14(7) separator between two inline elements that a text
extraction would otherwise read as one word. `renderToStaticMarkup` emits no indentation, no newlines
between elements and no separator comments, and `serialiseJsonLd` writes compact JSON, so
`lib/document/render.tsx` has no whitespace to remove and none was removed from it.

**Selectors, attributes and text kept.** Every selector named in `dom_parity.py`'s `CHROME_SELECTOR`
and `MARKUP_SELECTOR`, in `rendered_dup_check.py`'s `EXCLUDE_SELECTOR`, in `self_audit.py`'s
extraction and in `browser-checks.ts`'s measurements is untouched. In the interaction path
specifically: `ul.cd-interactions`, `ul.cd-rows`, `.cd-row-id`, `.cd-row-label` and `.cd-row-value`
wherever `EvidenceDisclosure` writes them, `.cd-section-heading`, `p.cd-paragraph`,
`details`/`summary`, `[data-furniture]`, `[data-block]`, `section.cd-block`, `h1`, `<main>` and the
`aria-labelledby="cd-interactions-heading"` binding. `data-anchored` is written by `QuestionBlock`
and was not touched. There is no `data-markup` attribute in this repository: what the template
declares markup is the class list in `dom_parity.MARKUP_SELECTOR`, and that list is unchanged.
